## 印の読み方：一般的な仕組みか、R4 独自か

ハーネスの仕事の多くは R4 の発明ではありません。以下の各仕組みには、スライドの
色付きバッジと同じ 3 種類の印を付けています。

| 印 | 意味 |
|---|---|
| **【一般的な仕組み】** | 主要なエージェント実装（Claude Code・Claude Agent SDK、OpenAI Agents SDK、opencode、LangChain・LangGraph）に共通する仕組み。一度覚えればどこでも通用します。 |
| **【一般的な仕組み・R4 の設定】** | 仕組みは一般的ですが、数値や選択は R4 独自です（印の横に R4 の値を書きます）。 |
| **【R4 独自】** | 上の実装にはなく、R4 が加えたもの。多くは小さな手元のモデル、共用の HPC 基盤、研究データのためです。 |

比べると分かりやすい箇所では、「他の実装では：」として、同じ仕事を他の実装が
どう行うかを 1〜2 例挙げます。

## 1. 文章はトークンになる（スライド 12）

**【一般的な仕組み】** すべての LLM（大規模言語モデル）に共通する性質です。
R4 自身は文章を分割せず、テキストのまま送ります。分割するのはモデルサーバ
（Ollama、vLLM）です。

モデルは文字を見ていません。トークナイザ（モデルごとに決まった、文章と番号の
変換辞書）が文章を固定の語彙（ここでは 151,665 種類）の断片に切り分けます。
この断片がトークンで、モデルが見るのはその番号だけです。測定結果（`␣` は
先頭の空白）：

| 文章 | 文字数 | トークン |
|---|---|---|
| `The Pn wave arrived 33.5 s after the earthquake.` | 48 | 15：`The` `␣P` `n` `␣wave` `␣arrived` `␣` `3` `3` `.` `5` `␣s` `␣after` `␣the` `␣earthquake` `.` |
| `紀伊水道の地震の深さは 12 km だった。` | 22 | 17：`紀` `伊` `水` `道` `の` `地震` `の` `深` `さ` `は` `␣` `1` `2` `␣km` `␣` `だった` `。` |
| `p_picks.csv` | 11 | 4：`p` `_p` `icks` `.csv` |

注目する点：

- **33.5 は 3・3・.・5 の 4 トークンです。** モデルは数を数として見ていない
  ので、計算はモデルではなくツール（Python）に任せます。
- 「Pn」も ` P` と `n` の 2 トークンです。専門用語でも 1 つの単位とは限りません。
- 日本語は英語より 1 文字あたりのトークン数が多くなります（22 文字で 17、
  英語は 48 文字で 15）。漢字がバイト単位の 2 つの断片に分かれることさえ
  あります（測定では、観測所の「観」が読めない 2 つの断片になりました）。
- トークン数は 2 つの点で重要です。コンテキストウィンドウ（§6）の大きさは
  トークンで数え、外部の AI サービスはトークン単位で課金します。

## 2. モデルの仕事は 1 つ：次のトークンに確率を付ける（スライド 13）

**【一般的な仕組み】** どの実装の裏にあるどのモデルでも同じです。R4 のチャットの
処理は、この確率を読みません。

それまでの全トークンを受け取ると、モデルは語彙のすべてのトークンに確率
（合計 1）を付けます。ハーネスがその中から 1 つ選んで末尾に追加し、もう一度
モデルに尋ねます。この繰り返しが「文章を書く」ということです。温度 1 での
測定結果：

| プロンプト | 次のトークンの上位 | 不確かさ |
|---|---|---|
| "Seismic waves refracted along the Moho and recorded far from the source are called head ___" | `␣waves` 0.87 · `waves` 0.06 · `␣and` 0.01 · `␣wave` 0.01 | 1.12 ビット |
| 「地震波には P 波と S 波があり、先に到達するのは ___」 | `␣P` 0.70 · `␣S` 0.07 | 2.72 ビット |

「ビット」は分布のエントロピー（確率がどれだけ散らばっているかの尺度）です。
0 なら確実、17.2 なら 151,665 個のトークンがすべて同じ確率という意味です。
学習で何度も見た物理の知識では、分布が鋭くなります。

## 3. 温度：どれだけ大胆に選ぶか（スライド 13）

**【一般的な仕組み・R4 の設定】** R4 は既定で **T = 0.4** を送ります
（`_DEFAULT_TEMPERATURE`、`companion/agent.py:248`）。環境変数
`R4_COMPANION_TEMPERATURE`（0〜2）で変えられ（`agent.py:251-264`）、
サブエージェント（親のエージェントが仕事の一部を任せる子のエージェント、§8）も
同じ値を使います。`top_p` は `R4_COMPANION_TOP_P` を設定した
ときだけ送ります。他の実装では：OpenAI Agents SDK は
`ModelSettings(temperature=…)`、LangChain はチャットモデルの生成時に指定します。
Claude Code では設定できません。

選ぶ前に、確率は温度 T によって形を変えられます（p_i ∝ exp(z_i / T)。z_i はモデルが
各トークンに付ける生の点数で、ロジットと呼びます）。
「head ___」のプロンプトでは、` waves` の確率は **T = 0.2 で 1.00、T = 1.0 で
0.87、T = 1.5 で 0.38** でした。T が低いとほぼ常に最上位のトークンを選ぶので、
結果を再現しやすく、解析に向きます。T が高いと選択が散らばるので、発想を広げる
のには向きますが、数値には向きません。再現性が必要な解析では、
`R4_COMPANION_TEMPERATURE=0 r4` でコンソールを起動します。同じ依頼で答えが
違うときは、多くの場合このサンプリング（確率に従った抽選）のせいです。
**温度は知識を増やしません。** すでにある分布を鋭くするか、平らにするだけです。

## 4. 知らなくても、モデルはトークンを選ぶ（スライド 14、29）

**【一般的な仕組み】** モデル自体の振る舞いです。実装ごとに違うのは対策
（検索、引用、検証）だけで、R4 の対策は RAG と、基本プロンプトの根拠に関する
規則です（`agent.py:545-592`）。

架空の観測所のモホ面（地殻とマントルの境界）の深さ（28 km。ナレッジパック（演習で配る、
架空の観測所の資料一式）にだけ書いてある）は、どの学習データにもありません。温度 1 での測定結果：

| プロンプト | 次のトークンの上位 | 不確かさ |
|---|---|---|
| "Our observatory's reference model puts the Moho under the Kii Channel at a depth of ___" | `1` 0.26 · `3` 0.16 · `2` 0.14 · `4` 0.11 · `7` 0.07 · `5` 0.07 | 3.03 ビット |
| 同じ文の前に KRSO-1D v2（架空の観測所の参照速度モデル）の段落を置く | **`2` 0.54** · `1` 0.16 · `3` 0.14 · `4` 0.06 | 2.08 ビット |
| 「私たちの観測所の参照モデルでは、紀伊水道の下のモホ面の深さは ___」 | `1` 0.26 · `2` 0.18 · `3` 0.14 | 3.38 ビット |
| 同じ文の前に日本語の段落を置く | `2` 0.27 · `1` 0.24 · `3` 0.13 | 2.93 ビット |

段落がないと、確率はいろいろな数字に散らばります。温度を 0.2 に下げても、
英語のプロンプトでは 87 %、日本語のプロンプトでは 82 % の確率で、モデルは「1…」と
書き始めます。流暢で自信ありげですが、作り話
です。**これがハルシネーション（もっともらしい作り話）です。バグではなく、
根拠がないときの通常の仕組みです。** 流暢さは知識ではありません。

段落を前に置くと、正しい最初の数字「2」が最上位になります。英語では T = 1 で
54 %、T = 0.2 で 99.7 % です。日本語では小さなモデルの確信はずっと弱く、
T = 1 で 27 % 対 24 %、T = 0.2 で 64 % 対 34 % でした。**RAG は確率を正しい方へ
動かしますが、正解を保証はしません。** だからこそ、引用された出典を自分で
確かめます。演習で使う 7B のモデルに R4 の指示を組み合わせると、もっとよく
答えます。Lab 1.4 で自分で測ってみてください。

## 5. 知識の在りか：学習と推論（スライド 15）

**【一般的な仕組み】** 外部のサービスでも手元のモデルでも同じです。ここで R4 側が
選んでいるのは、単体版スタック（自分の PC 1 台で R4 と UMRS を動かす構成、
stand-alone）がメモリ量に応じてモデルを選ぶことだけです
（`deploy/standalone/lib/model.sh:7-10`）。

**学習**はモデル開発者のところで一度だけ行われます。数兆トークンの公開テキストで
数十億個の数値（パラメータ）を調整し、ある時点（知識のカットオフ）で終わります。
**推論**（学習済みモデルで答えを出すこと）は質問のたびに、手元の PC で行われます。
パラメータは読むだけで、**変わりません**。会話によってモデルが学習することは
ないので、新しい知識はコンテキストから入れる必要があります。

| モデル（スタックが RAM 量で自動選択） | パラメータ数 | 16 ビット | 4 ビット（ダウンロード版） |
|---|---|---|---|
| `llama3.2:3b` | 3 B | 約 6 GB | 約 2 GB |
| `qwen2.5:7b` | 7 B | 約 14 GB | 約 4.7 GB |
| `qwen2.5:14b` | 14 B | 約 28 GB | 約 9 GB |
| `qwen3:30b`（MoE：1 トークンあたり約 3 B が働く） | 30 B | 約 60 GB | 約 18.6 GB |

必要なメモリはおよそ「パラメータ数 × 1 パラメータのバイト数」です（重みだけの
値で、コンテキストの分は別に必要です）。4 ビットに量子化（数値の精度を落として
小さくすること）するので、70 億パラメータのモデルが PC に収まります。その代わり
精度は少し下がります。MoE（mixture of experts、混合エキスパート）型のモデルは 300 億
個のパラメータをすべて持ちますが、1 トークンごとに使うのは約 30 億個なので、
大きさの割に速く動きます。ただしメモリは全体の分が必要です。

## 6. コンテキストウィンドウ：モデル唯一の作業記憶（スライド 17）

**【一般的な仕組み】** チャット形式の API を使う実装はどれも、呼び出しのたびに
会話全体を送り直します（Claude Code、OpenAI Agents SDK の `Runner`、opencode、
LangChain）。サーバ側に状態を持たせる方式でも、送り直しが見えなくなるだけで、
なくなるわけではありません。

モデルがセッションについて知っていることは、すべて 1 回のリクエストに
収まっていなければなりません。システムプロンプト、`R4.md` の規則、ツールの定義、
検索で得た文章、これまでの会話、ツールの結果です。この 1 回に入る量の上限が
コンテキストウィンドウで、単体版スタックでは **32,768 トークン**です
（`OLLAMA_CONTEXT_LENGTH`、`deploy/standalone/env/base.env:36`）。R4 はさらに
小さい**予算**で計画します。ウィンドウ × 0.90 − 4,096 で、32k なら
**25,395 トークン**です（`companion/context_budget.py:17-18, 80-85`）。

- モデルは**ステートレス**（状態を持たない）です。呼び出しの間に何も覚えて
  いません。ハーネスが毎ターン、すべてを送り直します。
- ウィンドウにないものは、モデルにとって存在しません。
- 50 MB の CSV は入りません。全部を読ませるのではなく、計算を頼みます。
- このウィンドウの中身こそ、外部の AI サービスに見えるものです。

コンソールで `/context` と入力すると、自分のセッションの実際の値が表示されます。

> **補足：** R4 はウィンドウの大きさを、まずモデルサーバがエンドポイントに登録した値から
> 取ります（単体版スタックは `max_model_len` = 32,768 を登録します。
> `companion/context_budget.py` の `resolve_model_context_limit`）。モデル名の表
> （`model_context.py:73,95`。`llama3.2` と `qwen3` は 131,072）を使うのは、
> エンドポイントの一覧が読めないときだけです。Ollama に直接つなぐモデルは、Ollama の
> `/api/ps` と `/api/show` から「学習時のウィンドウ」と「実際に提供されているウィンドウ」の
> 小さい方を使い、Ollama が答えないときは 32,768 とします（`companion/ollama_window.py`、
> 2026-10-30）。`R4_MODEL_CONTEXT_WINDOW` はどちらよりも優先され、`/context` は使用中の
> ウィンドウと予算を表示します。
> （2026-10-29：以前ここにあった「既知の問題」は、エンドポイントの値が優先されるため
> 当たらないので削除しました。）

## 7. 文章から操作へ：ツール呼び出し（スライド 18）

**【一般的な仕組み】** Claude の `tool_use` / `tool_result`、OpenAI の
function calling（Agents SDK の `@function_tool`）、opencode のツール、
LangChain の `bind_tools`。どれもモデルが依頼し、ハーネスが実行します。ループは
どこでも同じで、JSON の形が違います(Anthropic の `tool_use` は `input` が
オブジェクトで、結果は user メッセージ内の `tool_result` ブロックで返す。OpenAI の
Responses API は `function_call` / `function_call_output`)。クラウドの API が用意する
ツール(Web 検索、コード実行)は、事業者のサーバで動きます。

モデルは**何も実行しません**。ツール名を書いた要求を出すだけです。実行するか
どうかを決め、実行し、結果をモデルに見せるのはハーネスです。実際の形は次の
とおりです（OpenAI 互換の `/v1/chat/completions`。既定ではゲートウェイ
`<gateway>/gw/llm` 経由。エージェントのラウンドはストリーム（少しずつ届く形式）で
受け取って組み立てます。`client.py:1444-1535`。内容は短縮。2026-11-07 確認）：

```text
① ハーネス → モデル
POST <gateway>/gw/llm/v1/chat/completions
{"model": "qwen2.5:7b", "temperature": 0.4, "stream": true,
 "messages": [{"role": "system", "content": "..."},
   {"role": "user", "content": "How many stations are in p_picks.csv, and which is farthest?\n\n<turn_context>...</turn_context>"}],
 "tools": [{"type": "function", "function": {
   "name": "python_exec", "description": "Run Python ...",
   "parameters": {"type": "object", "properties": {
     "code": {"type": "string", ...},
     "timeout": {"type": "integer", "default": 180, ...}},
     "required": ["code"]}}}, ...]}

② モデル → ハーネス：要求で、まだ何も実行していない（少しずつ届き、R4 が組み立てる）
{"role": "assistant", "content": null,
 "tool_calls": [{"id": "call_1", "type": "function",
  "function": {"name": "python_exec",
   "arguments": "{\"code\": \"df = pd.read_csv(...); ...\"}"}}]}

③ ハーネスが実行し、結果を加えてもう一度モデルを呼ぶ
{"role": "tool", "tool_call_id": "call_1",
 "content": "25 stations; farthest JHT 267.6 km"}
```

ツールの定義は別の JSON の欄で送り、モデルサーバがプロンプトの文章に書き込み
ます（Qwen ではシステムの部分）。そのため入力トークンを使います（`python_exec` の
定義：`companion/tools.py:1782-1798`）。`tool_calls` を持つ assistant の
メッセージ（モデルが送れば `reasoning_content` も）の後に、呼び出し 1 つにつき
`role: tool` のメッセージが 1 つ続きます（`_record_tool_round`、
`companion/agent.py:3109-3159`）。

R4 がこの周りに加えているもの：

- **【一般的な仕組み・R4 の設定】本文からの読み取り。** 構造化されたツール
  呼び出しに対応しないモデルでは、R4 が返答の本文からツール呼び出しのタグ
  （`<tool_call>{json}</tool_call>`、`<invoke name=…>`、Kimi 独自の書式）を
  読み取ります。順番は、ネイティブの `tool_calls` → `<tool_calls_section_begin>`
  → Kimi の `<|open|>` → `<tool_call>` / `<invoke>` です（`_extract_tool_calls`、
  `companion/agent.py:5062-5085`）。考え方は ReAct（思考と行動をテキストで
  交互に書かせる手法）にさかのぼります。現在はこの読み取りを vLLM や Ollama の
  サーバ側で行うことが多く、Claude Code と OpenAI Agents SDK はネイティブの
  ツール呼び出ししか受け付けません。R4 はどのモデルでも動くよう、クライアント側
  で読み取ります。
- **【R4 独自】引数の修復と null の除去。** 壊れた JSON は、拒否する前に修復を
  試みます（制御文字、文字列として送られた配列や辞書、末尾の余計な文。
  `_repair_tool_arguments`、`agent.py:1721-1751`）。省略可能な引数に明示的な
  `null` が入っていれば外し、ツールの既定値を使わせます（`_without_null_optionals`、
  `agent.py:980-990`。`llama3.2:3b` はこれで `file_read` を失敗させていました）。
  修復できない呼び出しや存在しないツールは、許可ゲートの前にエラーとしてモデルに
  返します（`agent.py:5204-5221`）。推測で補うことはしません。

## 8. R4 のエージェントループ（スライド 19）

**【一般的な仕組み】** 中心部分は共通です。モデルを呼び、依頼されたツールを
実行し、結果を加えて、モデルが答えるまで繰り返します。Claude Code・Claude
Agent SDK（query のループ）、OpenAI Agents SDK（`Runner.run`）、opencode
（セッションのループ）、LangGraph（`create_react_agent`）はすべてこの形です。

`_run_agentic_turn`（`companion/agent.py:3131-3241`）を簡略化したもの：

```python
# r4/src/r4/companion/agent.py（簡略版）
messages = [system, *history, user]  # システムプロンプト・履歴・今回の依頼
for round in range(1000):            # 上限
    messages += finished_background_agents()
    fit(messages)                    # 古いラウンドを短縮
    reply = model(messages, tools)   # HTTP 呼び出し 1 回（ストリーム）
    calls = reply.tool_calls or parse_tags(reply.text)
    if not calls:
        if empty or "Let me …:": nudge; continue  # ≤2 / ≤3
        if cut at output limit: raise cap, continue
        return reply.text            # ツールなしの返答で終了
    for call in calls:               # フック → 許可の判定 → 実行
        messages += tool_message(call, run(call))
    if called("final_output"): return its text
    guards()                         # 空回り・連続失敗の検査
    checkpoint_if_no_new_evidence(every=25)
return wrap_up_round()               # ツールなしで 1 ラウンド
```

**ターン**は自分の依頼 1 回、**ラウンド**はその中のモデル呼び出し 1 回です。
各行で R4 が行うこと、その数値、一般的かどうか：

| 行 | R4 が行うこと | 印 | 他の実装では |
|---|---|---|---|
| `range(1000)` と `wrap_up_round()` | 上限は `DEFAULT_TOTAL_TOOL_ROUNDS = 1000`（`agent.py:80`）。上限に達すると、**ツールなし**でもう 1 ラウンドだけ呼び、分かったことをモデル自身にまとめさせます。失敗したときは決まった形の要約で代えます（`_wrap_up_summary`、`agent.py:3699-3720`）。 | 一般的な仕組み・R4 の設定 | OpenAI Agents SDK の `max_turns`（既定 10、超えると例外）、LangGraph の `recursion_limit`（25 で強制停止）。opencode はステップ上限でまとめを促し、R4 はこれにならいました |
| `finished_background_agents()` | 終わったバックグラウンドエージェントの結果を、次のラウンドで user の `<subagent-notification>` メッセージとして 1 つ加えます。終わったものがなければ何も加えないので、キャッシュされた先頭部分は崩れません（G9、`agent.py:3242-3253`）。同時に動かせるのは 4 つまで（`async_agents.py:24`）。 | 一般的な仕組み・R4 の設定 | Claude Code のバックグラウンドエージェントと `<task-notification>` |

| `parse_tags` | 本文からの読み取り（§7）。 | 一般的な仕組み・R4 の設定 | — |
| 促し | **空の返答**には「続けて」と促します（最大 2 回、`_EMPTY_REPLY_MAX_NUDGES`、`agent.py:141`）。「Let me …:」のように**次の手順を宣言しただけで何も呼ばない**返答にも促します（最大 3 回、`agent.py:143-150`）。 | R4 独自 | 他の実装では、テキストだけの返答でターンが終わります |
| 出力上限 | `finish_reason = length`（出力上限で途中終了）のとき、まず出力上限を max(2 倍, +8,192) トークン、最大 131,072 まで引き上げて 1 回だけやり直します（G19a、`_escalate_output_budget`、`agent.py:3343-3372`）。それでも足りなければ、途中で切れた思考の末尾 12,000 字を添えて「続けて」と最大 4 回促し（`agent.py:110-128, 196-205`）、最後は理由を示して止めます。 | 一般的な仕組み・R4 の設定 | Claude Code も出力上限を 1 回引き上げ、その後「続きから」と最大 3 回促します |

| `checkpoint_if_no_new_evidence(25)` | 25 ラウンドごとに（`DEFAULT_SOFT_BLOCK_ROUNDS`、`agent.py:79`）、新しい手がかりが得られたかを比べます。得られていればそのまま続けます。**得られていなければ**確認用のメッセージを差し込み、モデルに ① ここまでに分かったこと ② 次に試すことと理由 ③ この方針を続けるべきか、を書かせ、その後も**続行**します（`_block_boundary_control`、`agent.py:3666-3697`、メッセージは `agent.py:1046`）。停止ではありません。 | R4 独自 | 同等のものはありません。他の実装の上限は実行を止めます（LangGraph の 25 は強制停止の上限） |

**無人実行**（`R4_AUTONOMOUS=1`。ベンチマークや予約実行で使う）**【R4 独自】**：
ガードが働いても回答モードにはせず、促しを最大 3 回にとどめます。同じ呼び出しの
ガードも有効になります（結果にかかわらず、同じ名前と引数が 6 回続くか、A と B の
2 つが交互に繰り返されたとき。`agent.py:855-905, 3649-3663`）。出力上限の促しは
12 回まで許し、ターンを終える前に、依頼に照らした完了前の見直しを 1 回行います
（H4、`agent.py:3454-3485`）。

**サブエージェント**（**【一般的な仕組み・R4 の設定】**）：`spawn_subagent` は
同じプロセスとクライアントで、新しいコンテキストを使って動きます。進み具合の
確認（上の 25 ラウンドごとの確認）の間隔は親の半分の 12 ラウンド（25 ÷ 2 の
切り捨て）で、モデルと温度は親と同じです
（`agent.py:4498-4578`）。バックグラウンド版はすぐに戻り、終わってから結果を
知らせます（G9）。他の実装では：Claude Code の Task / Agent ツール、OpenAI
Agents SDK のハンドオフとツールとしてのエージェント、opencode の task ツール。

**代替モデル**（**【一般的な仕組み・R4 の設定】**、指定したときだけ）：
`R4_COMPANION_FALLBACK_MODEL` を設定すると、モデルの提供元で失敗が続いたときに

## 9. ハーネスが毎ターン送るもの（スライド 17）

**ツール定義はどこに入るか**(2026-11-05 のレビュー):R4 はリクエストの別の
`tools` 欄で送ります(単体構成で約 1.05 万トークン)。モデルが読む文章のどこに
置くかは、モデルサーバのチャットテンプレートが決めます。Ollama の Qwen 系の
テンプレートは、システムの内容の直後、履歴より前に書き込みます。そのため
スライド 17 では、ウィンドウを システム → ツール定義 → 過去のターン → 依頼文
(+ `<turn_context>`)→ このターンのツールのやり取り → 返答用の空き の順に
描いています。Llama 3.2 のテンプレートは、最後の依頼文の隣に置きます。

**【一般的な仕組み・R4 の設定】** system・メッセージ・ツールを 1 回の
リクエストで送るのはどの実装も同じです。R4 独自なのは、次の並べ方（手元の vLLM
や Ollama のサーバの先頭部分のキャッシュに合わせたもの）と、ターンをまたいで
**古いツールのやりとりを送り直さない**ことです。Claude Code も変化する状態を
user のメッセージ（`<system-reminder>` ブロック）に入れますが、ツールの呼び出しと
結果は要約するまで送り直します。opencode もツールの部分を残し、古い出力を
間引きます。

順番は次のとおりです（`_build_messages`、`agent.py:4580-4607`、
`_system_message`、`agent.py:4609-4633`）：

1. **system**：基本プロンプト、ワークスペース（作業フォルダ）、スキル一覧
   （スキルごとに 1 行）、指示ファイル、HPC サイト（2 つ以上あるときだけ）。
2. **history**：これまでの質問と回答。**テキストのみ**で、古いツールの呼び出しと
   結果は送り直しません（`session_turns.py:92-93`）。
3. **user**：今回の依頼。その**末尾**に `<turn_context>` ブロックが付きます。
   中身は、有効なスキルの本文、記憶（`~/.config/r4/companion/memory.json` に
   保存されたキーと値のメモ）、プロジェクトの状態、`UserPromptSubmit` フックの
   出力です（`session.py:1137-1151`、`turn_context.py`）。RAG のルータ（§14）が
   オンのときは、検索で得た文章 `[S1] [S2] …` が依頼文の**前**に付きます
   （`retrieval_router.py:968-995`）。
4. **tools**：全ツールの JSON スキーマ（ツールの定義）を名前順に並べたもの。
   **毎ターン同じ配列**です（`_tools_to_openai_schema`、`agent.py:620-634`）。

**この順番の理由：先頭部分のキャッシュ。** モデルサーバは、以前に見た
リクエストの先頭部分の計算を省けます（プレフィックスキャッシュ）。そこで、
変わらないものを先頭に置き、ターンが変わってもバイト単位で同じに保ちます。
system と tools が変わるのは、セッション中の出来事（拒否したツールを外す、
MCP サーバ（外部のツールをつなぐ共通規格 MCP のサーバ、§12）が増える、
`R4.md` を編集する）があったときだけです。変化するものは
依頼文の末尾に付けます。スキルのツール制限が、配列からツールを外すのではなく
呼び出しを**拒否する**形になっているのも同じ理由です（`session.py:970-997`）。
外すと先頭部分が変わり、キャッシュが無駄になります。他の実装では：Claude Code は
Anthropic API のキャッシュ区切りを指定し、OpenAI は長い先頭部分を自動で
キャッシュし、vLLM には自動の先頭部分キャッシュがあります。

**指示ファイル**（**【一般的な仕組み・R4 の設定】**）：起動したフォルダから
上位へたどり、`R4.md`、`AGENTS.md`、`agent.md`、`AGENT.md`、`CLAUDE.md`、
`OPENCODE.md` のうち見つかったものを**それぞれ**読み込みます（同じ名前は最も
近いもの 1 つ、この順番）。1 ファイル 4,000 字、合計 8,000 字までです
（`briefing.py:55-160`）。毎ターン読み直すので、`R4.md` を編集すれば次の依頼から
効きます。一方、スキルはセッションの開始時に 1 回だけ探します（`session.py:355`）。
他の実装では：Claude Code は `CLAUDE.md`、opencode と Codex は `AGENTS.md` を
読みます。OpenAI Agents SDK と LangChain にはファイルの決まりはありません。

## 10. ウィンドウをあふれさせない工夫（スライド 20）

**【一般的な仕組み・R4 の設定】** 長いセッションを扱う実装はどれも、打ち切りと
要約を行います。下の数値は R4 のものです。最後の段だけは **【R4 独自】** です。

| 段 | R4 が行うこと | コード |
|---|---|---|
| トークン数の推定 | 文字数 ÷ 比率で推定します。比率は 3.5 から始め、応答のたびにサーバが返す実際のトークン数（`usage.prompt_tokens`）で補正します（移動平均、重み 0.4、1 トークンあたり 1.5〜8 字の範囲）。トークナイザは呼びません。比率には 1.5 字の下限があるので、日本語（1 トークンあたり約 1〜1.3 字）が多い会話では、補正した後も少なめに見積もります。 | `context.py:44-57, 268-300` |
| ツールの出力が大量 | python・シェルの出力が 32,000 字を超えると、先頭 20,000 字と末尾 8,000 字だけ残します。結果が 40,000 字を超えると先頭と末尾だけにし、120,000 字を超えると `.r4/outputs/` に保存して、先頭 2,000 字と末尾 1,000 字だけを送ります | `tools.py:132-138`、`agent.py:73`、`agent/large_response.py:38-50` |
| 1 ターンの中 | 直前のラウンドは全文を残します。ツールの出力がウィンドウの 25 % を超えると、古い結果を先頭と末尾 1,024 字ずつに短くします。最新 40 ラウンドより前のラウンドは 400 字にします（キャッシュを保つため、境目は 10 ラウンド単位で動かす）。どれも `tool_result_fetch` で読み直せます | `agent.py:2044-2168, 5484-5489` |
| ターンの間 | 次のリクエスト（と応答用に確保する 4,096 トークン）が予算の **80 %** に達するとき：① **マイクロコンパクト**。古いメッセージのうち 4,000 字を超えるものを先頭の約 1,333 字に縮めます（直近 6 件はそのまま、モデルは呼ばない）。これで収まれば終わりです（G11）。② 収まらなければ**コンパクション**（要約）。直近 6 件以外のメッセージを、そのターンのキャッシュされた先頭部分を使ってモデルが要約します。要約が 3 回続けて失敗したら、次に成功するまで機械的なまとめで代えます（G12 のブレーカー）。 | `session_turns.py:119-152`、`context.py:131, 186-245, 533-560` |
| それでも大きい | 追加のコンテキスト（記憶・プロジェクトの状態）を削る → 入りきらないツールの定義を外す → 収まる範囲で新しい履歴だけを残す（**残す件数の下限はない**） | `context.py:403, 738-780` |

**計算例**（`qwen2.5:7b`、ウィンドウ 32,768 トークン）：予算 = 32,768 × 0.90
− 4,096 = 25,395。プロンプトと応答用の 4,096 の合計が予算の 80 %（20,316）に
達すると要約が始まります。つまり、プロンプトが約 **16,200 トークン**、ウィンドウの
約半分を超えたときです。

他の実装では：Claude Code は上限の近くで自動的に要約し（そのブレーカーも 3 回の
失敗で働きます）、`/compact` もあります。opencode はあふれたときに要約し、
LangChain には要約用のミドルウェアがあります。Claude Code も長いシェルの出力を
切り詰めます（約 30,000 字）。リクエストを収めるためにツールの定義を外すのは
珍しく、他の実装は普通はリクエストを失敗させます。

実際の使い方：要約で細部が失われることがあるので、長いセッションでは重要な
数値を言い直し、「ファイル全体を読んで」ではなく計算を頼みます。

混同しやすい「再試行」は 2 種類あります。事業者側の一時的なエラーは合計 3 回まで
試します（`agent.py:4847-4852`、`R4_COMPANION_TRANSIENT_RETRIES`）。コンテキスト
超過のエラーでは、古いメッセージの 4 分の 1 を削って**1 回だけ**再試行します
（`agent.py:696-718, 4786-4794`）。スライドには仕組みだけを載せ、回数などの数値は
ここに残しています。

## 11. 安全装置：許可ゲートと選択式のサンドボックス（スライド 21）

**【一般的な仕組み】** 危険なツールの実行前に確認するのは、どの実装も同じです
（Claude Code の許可の確認、opencode の allow / ask / deny、OpenAI Agents SDK の
ツール承認、LangChain の human-in-the-loop ミドルウェア）。判定の順番といくつかの
段は R4 独自です。

呼び出しはこの順に進みます。有効なスキルのツール制限（§12）→ 利用者の
**`PreToolUse` フック**（登録している場合。`~/.config/r4/hooks.json`。終了コード
2 で止め、標準エラー出力が理由になる。`user_hooks.py:1-30`、
`agent.py:5233-5241`）→ `PermissionManager.decide()`。`decide()` は次の表を上から順に調べ、
**最初に答えを出した段で結果が決まります**（`companion/permissions.py` の
`_LADDER` と各 `_rung_*` メソッド。ADR-104、2026-10-31）：

| # | 確認すること | 該当すれば | 印 | 段 |
|---|---|---|---|---|
| 1 | DENY（拒否）モードか？ | 拒否 | 一般的な仕組み・R4 の設定 | `_rung_deny_mode` |

## 12. スキルと MCP：必要なときに知識とツールを（スライド 23〜24）

**スキル**（**【一般的な仕組み】**）：段階的な読み込み（progressive disclosure）
で、Claude Code・Agent SDK の Agent Skills や opencode と同じ考え方です。毎ターン、
システムプロンプトにはスキルごとに一覧の 1 行だけが入ります（最大 40 行 ×
120 字、`skills.py:376-395`）。例：「residual-report — Writes a P-wave
travel-time residual report under the tutorial observatory's rules …」。
`SKILL.md` の本文全体は、スキルが有効になったときだけ `<turn_context>` に入ります。

R4 が加えているもの：

- **【R4 独自】キーワードによる有効化。** スキルの見出しにはキーワード
  （`x-r4-keywords`）を書きます。ターンの始めに、ハーネスが**依頼文**の中から
  キーワードを単語単位で探します（複数形の s / es も一致し、単語の一部には反応
  しない。`skills.py:159-177, 312-344`、`session_flow.py:30-53`）。一致すれば
  **このターン**から本文が入り、依存するスキルも一緒に有効になります。モデルが
  `activate_skill` を呼んで有効にした場合は、**次のターン**から入ります
  （`session.py:375-394`）。日本語のキーワードも使えます（単語の境目として見るのは
  英字と数字だけ）。英語のキーワードは日本語の依頼文には一致しないので、日本語用の
  キーワードも書いておきます。他の実装では(2026-11-05 に文書を確認):Claude
  Code・opencode・Codex では、説明文を読んだモデルが判断するか、利用者が名前で
  呼び出します(`/スキル名`、`$名前`)。キーワードで探す仕組みはどれの文書にも
  ありません(Claude Code はファイルのパスや import で一部のスキルを自動で読む
  だけ)。どちらが有効かは**測っていません**。キーワードは動きが予測できますが
  字面どおりで、言い換えや別の言語では一致しません。モデルの判断は言い換えも
  分かりますが、モデルが気づいたときだけ働きます。いつ使うかを説明文に書きます。
- **【R4 独自】スキルによるツールの制限。** 有効なスキルの `allowed-tools`
  （使ってよいツールの一覧）は、分野別のツールを絞り込みます。一覧にないツールは
  承認の前に拒否されます。ただし、シェル・python・ファイル操作・パッチのツールは
  拒否されません（`skills.py:187-221`）。ツールの配列自体も変わりません（§9）。
  Claude Code の `allowed-tools` は逆の働きで、一覧のツールを確認なしで使える
  ようにします。
- **【一般的な仕組み・R4 の設定】`tool_search`。** スキルの一覧にないツールが
  必要なときは、モデルが `tool_search` を呼びます。上位 5 件（単語単位の順位付け、
  よくある語は無視）が、次のターンから使えるようになります
  （`tool_search.py:20-35`、`session.py:985-995`）。Claude Code の ToolSearch は
  MCP ツールの定義を後から読み込むためのものです。R4 は定義を常に送り、検索は
  拒否を解除するためだけに使います。

**MCP**（Model Context Protocol）（**【一般的な仕組み・R4 の設定】**）：外部の

## 13. 埋め込み：意味を 768 個の数値で表す（スライド 27）

**【一般的な仕組み】** 検索の標準的な部品です（OpenAI の `file_search`、
LangChain のベクトルストア）。Claude Code には埋め込みによる検索はなく、grep や
glob でファイルを探します。

埋め込みモデルは、どんな文章もベクトル（数値の並び）に変えます。`e5-base-v2`
なら 768 個の数値です。意味が近い文章は、ベクトルが同じ方向を向きます（コサイン
類似度が 1 に近い）。向きにも意味があります。単語ベクトルの古典的な例が
**king − man + woman ≈ queen**（王 − 男性 + 女性 ≈ 女王。word2vec、Mikolov ほか、
2013）で、スライドでは説明用の例として示し、e5 では測っていません。2 つの
ベクトルの比べ方は**コサイン類似度** = a·b /（|a||b|）で、向きがそろうと 1 です。e5 の
ベクトルは長さ 1 なので、内積そのものです。UMRS は pgvector でこれを使って順位を
付けます（`<=>` はコサイン距離 1 − コサイン、全件を厳密に計算。
`umrs/src/umrs/knowledge/retrieval/dense.py:3, 157-165`）。スライド 27
では、質問 1 つ(「紀伊水道の下のモホ面の深さは?」)と 4 つの文の類似度も示します。
英語の例は `e5-base-v2` で、答え 0.81、言い換え 0.76、同じ話題の別の問い 0.68、
無関係な文 0.64。日本語の例では、英語専用の `e5-base-v2` が無関係な文を 2 位
(0.80)にし、`multilingual-e5-base` は正しい順(0.86 / 0.76 / 0.75 / 0.70)に
並べます。UMRS はモデルが想定する `query:` / `passage:` の接頭辞を付け
（`umrs/src/umrs/shared/utils.py:36-63`）、pgvector（PostgreSQL のベクトル検索
拡張）がコサイン距離で順位を付けます（`dense.py:157-165`）。

Lab 1.4 の質問について、英語のナレッジパックを節ごとに 1 チャンク（検索の
単位となる文書の断片）、計 17 チャンクとして測った結果：

| 順位 | スコア | 節 |
|---|---|---|
| 1 | 0.871 | 01 · History（v2 でモホ面 28 km、マントル 7.9 km/s に変更） |
| 2 | 0.858 | 03 · What we found |
| 3 | 0.856 | 05 · Reference models |
| 4 | 0.855 | 02 · Acceptance rules（PQ-3） |
| 6 | 0.848 | 01 · The model（表） |

スコアは近い値に固まっています（17 個すべてが 0.77〜0.87）。大事なのは値では
なく**順位**です。`e5-base-v2` は英語専用です。日本語のパックでは、規則の節
「採用の規則」（PQ-3）が 17 個中 15 位になります。`multilingual-e5-base` では
3 位で、1 位は「経緯」です。

## 14. RAG の全体像（スライド 26、28〜29）

**なぜ RAG か**（スライド 26）：モデルが知っているのは学習した文章だけで、自分の
観測所のモデルは知りません。学習し直すのは時間も費用もかかり、しかも出典は
示せません。RAG（検索拡張生成）が変えるのはモデルではなく、**モデルが読むもの**
です：自分の文書を検索する → 見つけた箇所にラベルを付けてコンテキストに入れる →
モデルはそれをもとに答えてラベルで出典を示し、最後は自分で出典を確かめる。

**【一般的な仕組み・R4 の設定】** 流れそのものは一般的な RAG（検索拡張生成）で
（LangChain の EnsembleRetriever も RRF で融合し、OpenAI の `file_search` は
ハイブリッド検索をサービスとして提供）、数値は R4 のものです。**【R4 独自】**
なのは、ナレッジがプロジェクトごとに UMRS 上にあることと、下のルータです。

**取り込み**はサーバ上の永続的なジョブとして実行されるので、中断しても状態が
残ります（`companion/knowledge_tools.py:139-230`）。アップロード → 分割（方式
`fixed-v0`、256 トークンのチャンク）→ 埋め込み（`e5-base-v2`）→ 索引付け。
さらにナレッジグラフの手順で、ローカルモデルが用語と関係を抽出します。

**検索**（`umrs/src/umrs/knowledge/retrieval/pipeline.py:3-21`）：質問を
ベクトル化 → 意味検索（dense：コサインで意味の近さを見る）→ 語句検索（lexical：
`PQ-3` や `KRSO-1D` のような語や識別子の一致を見る、BM25 などの古典的手法）→
2 つの順位を融合（RRF：各順位の逆数を足し合わせる、k = 60）→ 本文の取得 →
再ランキング（既定はオフ）→ 読み手のモデルに応じて上位 4〜6 件に絞る。
**検索にチャットモデルは使いません。**

**R4 では**（`companion/retrieval_router.py`）、経路が 2 つあります：

- **エージェント判断**：`R4_RAG_ROUTER=off`（**既定**）。エージェントが必要と
  判断したときに `search_docs` をツールとして呼びます。結果は
  `[label] <file> › <section>` の形の通常のツール結果として返ります
  （`tools.py:2560-2575`）。
- **自動経路**：`R4_RAG_ROUTER=on`。ほとんどのターン（スラッシュコマンド、短い
  相づち、コード作業の依頼を除く）で、ラウンド 1 の前にハーネスが検索し、
  `[S1]`、`[S2]` … のラベル付きの文章を依頼文に入れます。量は読み手のモデルの
  規模で決まり、`qwen2.5:7b`・`qwen2.5:14b`・`qwen3:30b` では **4 チャンク・
  2,000 トークン**、`llama3.2:3b` では **3 チャンク・1,200 トークン**です。
  コンテキスト予算の 12 % は超えません（`context_budget.py:25, 51-77`。32k では
  この上限は 3,047 トークンで、実際には効きません）。プロンプトインジェクションと
  判定されたチャンクは除きます。

他の実装では：LangChain の 2 段階の RAG チェーンは毎回検索します。OpenAI の
`file_search` や Claude Code 自身の検索は、モデルが判断します。2 つの経路を
ターンごとに使い分けるルータは R4 独自です。

**`[S1]` のラベルは R4 独自の書式**（ADR-093 D-4）で、OpenAI の決まりではありま
せん。まとめは `<passages>` の中に `[S1] 出典 › 節` を並べ、そのあとに
「cite passages as [S1]」という指示と質問を置きます
（`r4-contracts/src/r4_contracts/context_pack.py`）。番号はセッションを通して
続きます（`evidence_ledger.py`）。OpenAI の Chat Completions API には引用の決まり
がなく、Responses API の `file_search` は `file_citation` という注釈を返し、
Anthropic の API には文書の引用機能があります。どちらも構造化された項目で、本文中
のラベルではありません。

**効くのか？（スライド 29）**：同じ 3B モデルに、次のプレーンテキストをそのまま
入れて測りました（`next_token_probe.py` の `lab_ja` / `lab_rag_clear_ja` /
`lab_rag_ja`）。2026-11-07 のレビューで、RAG が効く条件を示すため、はっきりした
記述を加えました。

- A：`私たちの観測所の参照モデルでは、紀伊水道の下のモホ面の深さは `
- B（はっきりした記述）：`KRSO-1D v2(近畿地域地震観測所の参照モデル):紀伊水道の下の
  モホ面の深さは 28 km。` ＋空行＋A
- C（表のような記述。18 km も含む）：`KRSO-1D v2(…):上部地殻 0〜18 km は 5.9 km/s、
  下部地殻 18〜28 km は 6.7 km/s、深さ 28 km のモホ面より下のマントルは 7.9 km/s。`
  ＋空行＋A

| | A・質問だけ | B・はっきりした記述 | C・表のような記述 |
|---|---|---|---|
| 最も確率の高い答え | 100 km | **28 km** | **28 km** |
| ちょうど「28 km」の確率、温度 0.4（R4 の既定） | 0.1 % | **98 %** | 42 % |
| ちょうど「28 km」の確率、温度 1 | 0.5 % | 62 % | 9 % |

英語のプロンプトでは温度 0.4 で 0.5 % / 99.96 % / 75 %。RAG が効くのは、検索した
文章が事実をはっきり書いているとき。似た数値がいくつもある記述では、間違える
余地が残ります。「ちょうど 28 km」
= p(「2」) × p(「8」|「2」) × p(その後に数字が続かない)で、値は
`next_token_probe.json` の `answer_28` にあります。RAG は確率を正しい方へ動かし
ますが、答えを保証はしません。引用元を自分で読みます。

**`[S1]` は誰が扱うのか**:R4 が各箇所の前にラベルを書き、引用するよう指示します。
モデルはラベルを文字列として写すだけです。回答のたびに R4 の `citation_check`
(モデルは使わない)が出典を並べ、検索していないラベルや、引用箇所にない数値を
指摘します。コンソールは出典をチップで表示します。`R4_RAG_VERIFY=strict` では
根拠のない回答を「NOT ENOUGH INFO」にします。自動のやり直しはありません。

**RAG で正解を保証できるか(スライド 30)**:できません。「上の資料だけをもとに
答え、数値はそのまま写すこと」を加えても(プロンプト C)良くなりませんでした。
温度 0.4 で「ちょうど 28 km」の確率は、英語で 73 %(指示なしで 75 %)、日本語で
30 %(指示なしで 42 %)。日本語では最も確率の高い答えが、記述の中の別の数値
**18 km** になりました。信頼は確かめることで得ます。引用元を開く、数値の隣に
根拠の文を引用させる、値はツールでファイルから読ませる、結果をテストする。
検索の改善、大きなモデル、低い温度は確率を上げるだけです。

## 16. R4 のどこに何があるか

| 部品 | ファイル（`r4/src/r4/…`） |
|---|---|
| エージェントループ | `companion/agent.py`：`_run_agentic_turn` |
| モデル呼び出し（OpenAI 互換） | `client.py` |
| ツール（`python_exec`、`file_read` など） | `companion/tools.py` |
| 指示ファイル（`R4.md` など） | `briefing.py` |
| コンテキスト予算・要約 | `companion/context.py`、`companion/context_budget.py` |
| ターン間の要約の流れ | `companion/session_turns.py` |
| ターンごとのブロック（`<turn_context>`） | `companion/turn_context.py` |
| 大量のツール出力の退避 | `agent/large_response.py` |
| 許可ゲート | `companion/permissions.py` |
| 許可のルールファイル・保護パス（G14） | `companion/permission_rules.py` |
| ユーザ定義のフック（G13） | `companion/user_hooks.py` |
| スキル | `companion/skills.py`、`companion/builtin/` |
| `tool_search`（G18） | `companion/tool_search.py` |
| バックグラウンドエージェント（G9） | `companion/async_agents.py` |
| ビルド契約（作る機能と合否の記録を JSON で残す取り決め、まとめ参照）と、新しいコンテキストで見直すレビュー役（G15 / G16） | `companion/build_contract.py`、`companion/sprint_review.py` |
| MCP ツール | `companion/mcp_first_class.py`、`mcp.py` |
| RAG ルータ、ナレッジのツール | `companion/retrieval_router.py`、`companion/knowledge_tools.py` |
| 検索（サーバ側） | `umrs/src/umrs/knowledge/retrieval/` |

ここまでの仕組みはすべて、普通に読める Python のコードです。ハーネスは魔法では
なくエンジニアリングで、自分で読んで変えることもできます。興味のある人への
宿題：`_run_agentic_turn` と `PermissionManager.check()` を読んでみてください。

## まとめ：誰が何をするか（スライド 31）

| 層 | すること | できないこと | 調整方法 |
|---|---|---|---|
| モデル | 次のトークンに確率を付ける | 研究室の事情を知る・コードを実行する・覚えておく | モデルの選択、温度 |
| エージェントループ | ツールの要求を実際の操作に変え、繰り返す | 結果が正しいかを判断する | 自分の目標と合格基準 |
| ハーネス | コンテキストを組み立て、ツールを制御し、記憶を管理する | 弱いモデルを強くする | `R4.md`、スキル、許可 |
| ナレッジ | 正しい文章をモデルの前に置く | モデルがそれを使うことを保証する | 自分の文書、RAG のオン/オフ |

「モデルが自分の仕事を自分で採点する」問題への R4 の答え：無人実行では、ターンを
終える前に依頼に照らした見直しを 1 回行います（`agent.py:3454-3485`）。ビルド
契約（作るべき機能の一覧と合格の記録を `.r4/build/<名前>/` に JSON で残す取り決め。
エージェントは各機能の「合格」の印しか変えられない）では、読み取りと実行だけができるツールと、合否の基準が明確な評価表を持つ
レビュー役を、新しいコンテキストで動かします（`sprint_review.py`、G15）。
対話で使うときのレビュー役は自分自身です。依頼に書いた合格基準がその役目を
果たします（スライド 42）。
