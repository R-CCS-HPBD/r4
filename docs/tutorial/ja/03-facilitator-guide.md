## 期待される答え

- **Lab 1.1：** 2.5° 以内に 25 観測点。最も遠いのは **JHT、約 268 km**。
  読み取り値：Pg と Pb は 128 km まで、Pn は 132 km（JKS）から。合成データ：
  30 観測点、最も遠いもので 275 km。
- **Lab 1.2：** クロスオーバー距離（Pn が直接波より先に届き始める距離）は
  **約 130 km**（最後の Pb が 128 km、最初の Pn が 132 km）。合成データでは約
  102〜110 km。発展課題（値は本ガイドの作成者による計算）：1 層の式に h = 28 km、v2 = 7.9 km/s を
  入れると、v1 = 6.7 km/s で約 195 km、v1 = 5.9 km/s で約 147 km となり、観測より
  長い。観測より長くなるのは、式が震源を地表に置き（この地震は深さ 16 km で、より
  モホ面に近い）、地殻を 1 層として扱っているためである。数値よりも議論が大事。
- **Lab 1.3：** 合格基準のコマンドが通る。2 つの解答例
  （`answer_key/eikonal_numba.py`、`answer_key/eikonal_numpy_diag.py`）とも
  max |ΔT| = 0。ワークステーションでの 126 万格子点の計算時間：素の Python
  14.6 秒、NumPy 1.40 秒（約 10 倍）、Numba 0.24 秒（約 60 倍）。1 km 格子では
  117 秒と 1.5 秒（約 75 倍）。`bench.py --sizes 21 41 61` では Numba が 56〜62 倍。
- **Lab 1.4 の質問：** **KRSO-1D v2**（規則 RM-1）、**モホ面 28 km**、
  **マントル 7.9 km/s**、**|残差| > 2.5 秒**で棄却（規則 PQ-3）。根拠はナレッジパックの
  ファイル 01 と 02。パックが
  ないと、モデルは公開されているモデル名と教科書的なモホ面の深さを推測で答える
  しかない。**Lab 1.4 D：** レポートは KRSO-1D v2 を明記し、ISC を引用し、
  **JKS**（132 km の Pn。PQ-5 では 140 km 超が必要）を要確認とするはず。KRSO-1D v2
  では PQ-3 の限度を超える読み取り値はない（2026-10-27 の実行で最大の |残差| は
  約 1.2 秒、JKN2）。採用された 25 観測点は、PQ-7 の下限 8 を満たす。
- **Lab 1.5（2 km 格子）：** ak135 は平均 **−1.12 秒**、RMS **1.32 秒**。
  KRSO-1D v2 は **+0.04 秒 / 0.46 秒**。自分の残差と ISC の ak135 残差の差：
  2 km で −0.36 秒、1 km で −0.18 秒（1 km での ak135：−0.94 秒 / 1.14 秒）。
  合成データ：ak135 は −1.21 秒 / 1.38 秒（2 km）、1 km の KRSO-1D v2 では
  −0.13 秒 / 0.17 秒。
- **第 2 部のレポート（合成データ、4 km 格子、NumPy、手元で 54 秒）：** ak135 の
  RMS 1.48 秒（平均 −1.30 秒）、最良 0.21 秒（平均 −0.01 秒）。モホ面 26 km と
  28 km が同点。参考として、実際の読み取り値を 2 km 格子で解くと、162 モデル中の
  最良は 5.7 / 6.5 / モホ面 26 / 7.9 km/s で RMS 0.44 秒。合成データの最良は
  5.9 / 6.5 / モホ面 26 / 7.9 で 0.14 秒。
- **クイズ（スライド 43）：** Q1 いいえ。その知識はモデルではなく自分の文書にあり、
  ハーネス（RAG）がモデルに渡す。Q2 テストの範囲でだけ正しい。ベンチマークの
  max |ΔT| と実例でも確かめる。Q3 この経路ではモデルの速度が遅すぎる。あるいは
  震源位置・発震時刻（地震が起きた時刻）がずれている。

伝えるべき要点：この経路では ak135 の予測は約 1 秒遅い（Pn）。モホ面の深さと
下部地殻の速度はトレードオフ（一方を変えても他方で補える関係）にあり、RMS の差が
0.02 秒以内のモデルが複数ある。最良値が探索範囲の端にあるなら「範囲を広げる」
べきで、「見つけた」ではない。正しいモデルでも残差は 0 にならない（1 次精度の
解き方と、読み取りの誤差のため）。発震時刻と震源は ISC の解に固定している。

## 失敗クリニックの解答

参加者は各バンドルを `/workflow upload docs/tutorial/workflows/faults/<fault>` と
`/workflow run seismic-<fault> --param bucket=<b>` で実行し、
`/workflow results <id>` と `/job <id>` を読む。

| バンドル | 症状 | 修正 |
|---|---|---|
| f1-bad-entrypoint | `search_low` が実行前に失敗：`module 'steps' has no attribute 'ModelSearchSteps'` | `steps:ModelSearchStep` |
| f2-missing-key | `search_high` が `picks.csv` を読めない（そのキーが存在しない） | `picks_key: p_picks.csv` |
| f3-timeout | `search_low` が 5 秒の制限時間を超える（`debug_delay_seconds: 30`） | 遅延を削除するか `timeout_seconds` を増やす |
| f4-lost-parents | `rank` が探索ステップを待たずにすぐ始まり、順位付けする RMS の結果が見つからない（`next(...)` で `StopIteration`） | `depends_on: ["search_low", "search_high"]` |

4 つとも `r4 workflow lint`（形式の検査）を通過する。この点を強調すること。f1、
f2、f4 は 2026-10-27 に `run_local.py` で再現した（手元では f2 はもっと早く、
`run_local.py` が存在しないファイルを配置しようとする時点で失敗する）。f3 の
制限時間はサーバ側でしか強制されないので、**f3 はリハーサルで、稼働中の
単体構成のスタック（`./r4-local up` で起動するサービス一式）上で確認すること**。
