背景の解説：[04-background-model-agent-harness.md](04-background-model-agent-harness.md)

エージェンティックワークとは、AI エージェント（ツールを使って作業を進める AI）に
作業を任せ、人は目標と合格基準を決めて結果を確かめる働き方です。ここに載せた
手順はすべて 2026-10-29 にコードと照合しました。所要時間と残差（観測した到達時刻
− ソルバが予測した到達時刻）はワークステーションで測った値です（解答の全体：`docs/tutorial/data/README.md`）。
**作業はすべて R4 のコンソール（`r4` で開く、ターミナル内の操作画面）の中で
行います。** リポジトリのフォルダで一度だけ起動してください：

```bash
cd r4
source .venv/bin/activate
r4
```

**題材：地震波の初動。** P 波は、地震が起きたとき地震計に最初に届く波です。
実際の地震で観測された P 波の到達時刻をダウンロードし、エージェントと一緒に
3 次元の走時ソルバ（地震波が届くまでの時間を計算するプログラム）を速くし、
その予測を観測と比べます。

**対象の地震：** 2021-12-03、紀伊水道（和歌山沖）、ISC イベント
**621611300**。実体波マグニチュード mb 5.2、深さ 16 km、神戸から約 70 km、人的被害は
ありませんでした。
読み取り値（ピック：観測記録から読み取った P 波の到達時刻）は ISC Bulletin
（国際地震センターの地震カタログ）から取得します。使う場所では必ず次を引用して
ください：**International Seismological Centre (2026), On-line Bulletin,
https://doi.org/10.31905/D808B830** 。リポジトリにはこのデータの**コピーは
ありません**。Lab 1.1 でその場でダウンロードします。ネットワークにつながらない
場合は、**合成**データ `docs/tutorial/tasks/eikonal/data/synthetic-kii/`（架空の
地震、30 観測点）を使い、合成データだと明記してください。

## Lab 1.3 — エージェントによるコーディング：3 次元ソルバを速くする（15 分、スライド 35〜36）

`docs/tutorial/tasks/eikonal/eikonal_slow.py` は、アイコナール方程式
|∇T| = 1/v（T は初動の走時、v は速度）を、3 次元の格子の上で高速掃引法
（fast sweeping method：格子を決まった順に繰り返し更新して解く方法）によって
解きます。結果は正しいのですが、素の Python のループで書かれていて遅いです。
テストとベンチマークが**合格基準**です。エージェントが書いたコードを読まなくても、
正しいかどうかが分かります。

`/code on` でコーディングモードをオンにしてから、次のように依頼します：

> docs/tutorial/tasks/eikonal で作業してください。eikonal_slow.py は正しい
> ものの、地域規模の 3 次元格子には遅すぎます。同じ `solve()` を持つ
> my_fast.py を書いてください。`EIKONAL_IMPL=my_fast pytest test_eikonal.py`
> に合格し、かつ `python bench.py --impl my_fast --sizes 21 41 61` で max |ΔT|
> が 1e-6 未満になることが条件です。何を変えたのか、なぜ速くなるのかも説明して
> ください。

そのあと、合格基準を**自分でも**確かめます（max |ΔT| は、遅い参照版と自分の版
の走時の差の最大値）：

```text
!cd docs/tutorial/tasks/eikonal && EIKONAL_IMPL=my_fast python -m pytest -q test_eikonal.py
!cd docs/tutorial/tasks/eikonal && python bench.py --impl my_fast --sizes 21 41
```

`pytest` を毎回承認するのが面倒なら、**ユーザ用**のルールファイル
`~/.config/r4/permissions.json` に 1 行書くと、事前に許可できます（任意）：

```json
{"allow": ["shell_exec(prefix:pytest)"]}
```

リポジトリに含まれる `.r4/permissions.json` では、ask（確認）と deny（拒否）
しか効かず、許可はできません（背景解説の §11）。

（`/code test` はプロジェクト全体のテストを実行し、1 つのファイルだけを実行する
ことはできないので、ここでは使いません。）ワークステーションでの測定値
（実際の地震の格子を 1 回解く。格子間隔 2 km、31 × 174 × 234 = 126 万格子点）：

| ソルバ | 1 回の計算時間 | 高速化 |
|---|---|---|
| `eikonal_slow.py`（素の Python） | 14.6 秒 | — |
| NumPy、対角の平面ごとに更新 | 1.40 秒 | 約 10 倍 |
| Numba（Python 用の JIT コンパイラ。同じループをコンパイル） | 0.24 秒 | 約 60 倍 |

1 km 格子（990 万格子点）では、素の Python が 117 秒、Numba が 1.5 秒（約 75 倍）
です。1 km 格子は時間がかかるので、ターミナルのペインで試し、出力を
エージェントに渡しましょう：

```text
/term
cd docs/tutorial/tasks/eikonal && python japan_event.py --impl my_fast --h 1.0
/term share
```

ノート PC はワークステーションより遅くなりますが、速度の比はほぼ同じです。

エージェントの説明で確かめる点：Numba はアルゴリズムも更新の順序も変えない
ので、答えはまったく同じになります。NumPy では順序を変える必要があります。
1 回の掃引（sweep：格子を一方向に順に更新すること）の中では、i + j + k が
等しい平面の上の格子点どうしは互いに依存しないので、平面ごとに 1 回の配列演算で
更新できます。GPU でこの方法を動かすときも同じ考え方です。エージェントがこれ
以外の形で更新の順序を変えた場合は、max |ΔT| の行がその誤りを捕まえます。

### E — MCP ツールを 1 つ登録する

MCP（Model Context Protocol）は、外部のツールをエージェントにつなぐための
共通規格です。単体版の構成での手順を示します（2026-10-09 に検証、
`deploy/standalone/README.md` の §MCP）。Hatch（MCP サーバを配布・起動する R4 の
仕組み）のランタイムは手元のマシン上で動き、コンテナ内の UMRS からそこへ
接続できる必要があります。`/term` を開いて実行します：

```bash
export HATCH_REGISTRY_URL="$PWD/mcp-servers/hatch-registry"
export R4_HATCH_BIND_HOST=0.0.0.0
export R4_HATCH_ADVERTISE_HOST=host.containers.internal
r4 mcp hatch install platform-tools
r4 mcp hatch connect platform-tools
r4 mcp list -t
```

コンソールに戻り、`/mcp`（重ねて表示する画面）か `/mcp tools` でツールを
確認します。ここではループバック（自分のマシンの中だけの通信）以外からの接続を
受け付けても安全です。ランタイムはすべての呼び出しにランタイムごとの
ランダムなアクセストークン（合言葉にあたる文字列。モデルが読む「トークン」とは
別物）を要求し、そのトークンを UMRS に登録するからです。
エージェントからは、ツールが `mcp.<server>.<tool>` として見えます。手元の
`mcp.json` ファイルはエージェントからは**見えません**。UMRS を通じた登録が
正しい経路です（`/mcp register` はまだ実装されていません）。

次に、エージェントに呼び出させます。コンソールを再起動します（`/quit` のあと
`r4`）。セッションは開始時に MCP ツールを読み込むためです。依頼します：
*「プラットフォームで使えるモデルを教えて。platform-tools の MCP サーバを
使って。」* トレース（**Ctrl+O**）に `mcp.<server>.list_models` の呼び出しが
現れるはずです。その結果は汚染フェンスでは MCP の出力として扱われ、そこから
写した呼び出しでは確認を求められます。*（2026-10-30 の修正までは、
エージェントからの MCP ツールの呼び出しはエラーになっていました。）*

## Lab 1.5 — 自分のソルバと実際の地震（7 分、スライド 41）

速くしたソルバで、各観測点への到達時刻を予測できるようになりました。2 つの
速度構造モデルで実行します。全球モデル **ak135**（ISC も使っているもの）と、
ナレッジパックにある観測所のモデル **KRSO-1D v2**（RAG で得たモデル）です：

```text
/code run docs/tutorial/tasks/eikonal/japan_event.py -- --impl my_fast --data docs/tutorial/tasks/eikonal/data/kii-channel-2021-12-03 --model ak135
/code run docs/tutorial/tasks/eikonal/japan_event.py -- --impl my_fast --data docs/tutorial/tasks/eikonal/data/kii-channel-2021-12-03 --model krso
```

`/code run` はリポジトリのフォルダで動くので、パスはリポジトリからの相対パスで
書きます。スクリプト自身のフォルダが import の検索先に入るので、`--impl my_fast`
で自分の `my_fast.py` が見つかります。既定の制限時間は 60 秒です。ソルバが遅い
場合は、`--` の前に `--timeout 300` を付けてください。`--impl` を付けないと
遅い参照実装が使われます。答えは同じで、遅いだけです。

実行するたびに、データフォルダへ `residuals.csv` と `comparison.png` を書き出し
ます（2 回目は 1 回目を上書きするので、両方残したい場合は間でエージェントに
名前を変えてもらってください）。残差 = 観測 − 予測です。負の値は、波が予測より
早く着いたことを意味します。

期待される値（2 km 格子、25 観測点）：

| モデル | 平均残差 | RMS（二乗平均平方根） |
|---|---|---|
| ak135 | −1.12 秒 | 1.32 秒 |
| KRSO-1D v2 | +0.04 秒 | 0.46 秒 |

ak135 の場合、スクリプトは ISC 自身が公表している ak135 の残差（列
`isc_residual_s`）との比較も表示します。自分の ak135 の残差は、ISC の残差と
観測点ごとに同じ傾向で動き（ほぼ一定のずれを保って並行し）、平均のずれは
−0.36 秒です。1 km 格子（`--h 1.0`、Lab 1.3 のターミナルでの
実行）では −0.18 秒と半分になります。1 次精度の解き方（誤差が格子間隔にほぼ比例する解き方）が、格子間隔を細かくする
につれて収束している様子です。実際のデータで、自分のソルバが独立したソルバと
照合できたことになります。

合成データの場合：`--data docs/tutorial/tasks/eikonal/data/synthetic-kii` で、
ak135 は −1.21 秒 / RMS 1.38 秒。`--model krso --h 1.0`（データを作ったモデル）
では −0.13 秒 / 0.17 秒で、正しいモデルでも 0 にはなりません。ISC の列がない
ので、比較の行は表示されません。

そのあと、エージェントに尋ねます：*「residuals.csv を説明して。ak135 に対して
どの相が、どれだけ早く着いている？　それは地殻について何を示している？」*
（約 130 km より遠い Pn が約 1 秒早く着きます。実際の地殻は、ak135 の地殻の厚さ 35 km より
薄いということです。）架空の KRSO-1D v2 は、この実際の地震に対しても、探索した
162 個のモデルの最良（RMS 0.44 秒）とほぼ同じくらいよく合います。ただし、
読み取り値 25 個の地震 1 つだけでは、モホ面の深さは決まりません。深さと速度が
トレードオフ（一方を変えても他方で補える関係）になるからです（第 2 部）。

## 良い使い方 — 科学の依頼に入れる 4 つの要素（スライド 42）

データ · 目標 · 制約 · **合格基準**。例：*「docs/tutorial/tasks/eikonal/data/kii-channel-2021-12-03
の ISC の読み取り値（ISC Bulletin を引用）を使い、my_fast と 2 km 格子で
ak135 に対する P 波の残差（観測 − 予測）を計算して。読み取り値は変更しないこと。
合格基準：残差が isc_residual_s の列と観測点ごとに同じ傾向で動き、平均の差が 0.5 秒以内で
あること。」*
