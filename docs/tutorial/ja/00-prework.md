# 事前準備 — 当日までにノート PC を準備する

2026-10-29 · R4 + UMRS チュートリアル · 日本語 ([English](../en/00-prework.md))

**イベントの前に**必ず済ませてください。所要時間は 30〜60 分で、その大半は
ダウンロードの待ち時間です。当日は 5 分間の確認だけを行います。うまくいかない
場合は、手順 4〜5 の確認の出力を運営に送ってください。当日まで待たずにご連絡
ください。

## 1. 自分のマシンで動きますか？

| | 対応（テスト済み） | 可能な範囲で対応（未テスト） | 非対応 |
|---|---|---|---|
| OS | Linux x86_64、macOS | Windows 11 + WSL2 | WSL2 のない Windows |
| メモリ | RAM 16 GB 以上 | — | 16 GB 未満 |
| ディスク | 空き 15 GB（コンテナイメージを手元でビルドする場合は 30 GB） | — | それ未満 |
| コンテナ | Docker + Compose v2、または Podman 4.7 以上（`podman compose`） | — | Python 版の `podman-compose` |
| GPU | 不要 | NVIDIA の GPU があるとモデルが速くなる | — |

ほかに `git`、`python3`、`curl`、`nc`、`openssl` と、空いているポート
8080 および 5555〜5563 が必要です。スタック（ノート PC 1 台で動くサービス一式）は、メモリ量に合わせて
無料のモデルを選びます。12 GB 未満では `llama3.2:3b`、12〜24 GB では
`qwen2.5:7b`、GPU メモリが 12 GB 以上の GPU、または 24 GB 以上の Apple のユニファイドメモリ
（CPU と GPU が共有するメモリ）では `qwen2.5:14b`、48 GB 以上では `qwen3:30b`
です。ノート PC の CPU ではモデルの動作は遅いものの、使うことはできます。
回答に数十秒かかることを見込んでおいてください。

## 2. チュートリアルのリポジトリを取得する

```bash
git clone --recurse-submodules https://github.com/R-CCS-HPBD/r4.git
cd r4
git submodule update --init umrs     # --recurse-submodules なしで clone した場合
```

## 3. 手元のスタックを起動する（コマンド 1 つ）

```bash
./r4-local up
```

このコマンドは次のことを順に行います。

1. マシンの確認（メモリ、ディスク、ポート、ツール）
2. モデルの選択とダウンロード
3. 手元の UMRS（R4 の処理を実行する基盤：データベース、オブジェクトストレージ、
   モデルサーバ）をコンテナで起動
4. `r4` クライアントを `.venv/`（リポジトリ内の Python 仮想環境）にインストール
   （Python のパッケージ管理ツール [`uv`](https://docs.astral.sh/uv/) が必要です。
   ない場合はインストール方法を表示します）
5. スタックを `r4` の接続先 `standalone` として登録
6. 動作確認（チャット 1 回、文書のアップロード 1 回、検索 1 回）

`./r4-local up --yes` とすると、途中の質問にはすべて既定値で答えます。

チュートリアルはコンソール（TUI：ターミナル内で動く操作画面）で進めます。
コンソールには [`bun`](https://bun.sh) か、リリース版のバイナリ
（`r4 tui install` で入れる）が必要です。どちらもない場合、`r4` は画面を分割しない、
1 行ずつ入出力する簡単な画面で動きます。当日までにどちらかをインストールしておいて
ください。

## 4. スタックを確認し、コンソールを開く

ターミナルで：

```bash
./r4-local status
./r4-local doctor
source .venv/bin/activate
r4
```

ここから先、チュートリアルはすべて**コンソールの中**（`r4` が開く R4 の TUI）
で進めます。`/` で始まる行はコンソールのコマンドです。`!` で始まる行は、
ワークスペース（作業フォルダ）でシェルコマンドを実行します。コンソールから直接
実行でき、その出力はモデルにも渡ります。コンソールで：

```text
/source                 # standalone を選ぶ
/health                 # ゲートウェイ・エンドポイント・プラットフォームの状態：すべて緑？
/models                 # ./r4-local up でダウンロードしたチャットモデル
```

ゲートウェイは UMRS の入口となる API サーバ、エンドポイントはモデルなどの接続先です。
続けて、チャットに入力します：*1 文で挨拶して。*

## 5. 演習（Lab）用に追加する Python パッケージ 3 つ

エージェントは Python を手元のマシン上で実行するので、エージェントが使う
ライブラリがその環境に入っている必要があります。そのままコンソールで：

```text
!uv pip install --python .venv/bin/python matplotlib pandas numba
!python -c "import numpy, matplotlib, pandas, numba, pytest; print('labs ok')"
```

`matplotlib` と `pandas` は作図用です。`numba` は、Lab 1.3 で走時ソルバ（地震波が
届くまでの時間を計算するプログラム）を速くする方法の 1 つに使います。NumPy を
使う方法は `numba` なしでも動くので、お使いのマシンに `numba` をインストール
できない場合は、そのまま進めて運営に知らせてください。

`/health` がすべて緑で、1 文の回答と `labs ok` が返ってきたら、準備は完了です。
`/quit` でコンソールを閉じます。当日までは `./r4-local down` でスタックを
止めておいてください（データは残ります）。`./r4-local up` で再び起動します。

*コンソールの外で*（代わりの方法）：`r4 source use standalone`、`r4 doctor`、
`r4 chat "…"` を使えば、普通のターミナルから同じ確認ができます。

## 6. データはどこに置かれるか

ここまでの構成はすべてノート PC の上で動きます。ファイルと結果は手元の
オブジェクトストレージ（SeaweedFS：S3 互換のファイル置き場）に、文書のベクトル
（意味を表す数値の並び）は手元の Postgres + pgvector（ベクトル検索のできる
データベース）に、モデルは手元の Ollama（モデルを動かすサーバ）にあります。
外部の AI サービスには何も送信されません。別の構成を選ぶ場合とその方法は、
チュートリアルの中で扱います。

1 つの演習だけは、意図的にインターネットに接続します。エージェントが、実際の
地震で観測された到達時刻を、公開されている ISC Bulletin（国際地震センターの
地震カタログ）からダウンロードします（International Seismological Centre (2026),
On-line Bulletin, https://doi.org/10.31905/D808B830 ）。ノート PC から出ていく
のは、その地震のデータを求めるリクエストだけです。ネットワークにつながらない
場合、この演習では代わりに合成データ（計算で作った模擬の観測データ）の地震を使います。
