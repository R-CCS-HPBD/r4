# 24. A2L — Artifact and Agent Lineage

> **Audience:** End users, agent developers, and platform administrators  
> **Requires:** A2L sidecar deployed alongside the platform gateway  
> **CLI commands:** `r4 artifact`, `r4 run`

---

## What is A2L?

**A2L** (Artifact and Agent Lineage) is an optional platform sidecar that provides
**scientific provenance tracking** for computation artifacts.  Every dataset,
model checkpoint, report, or intermediate output produced by an agentic pipeline
can be registered as an *artifact*.  When one artifact is derived from another
(e.g. a cleaned dataset derived from raw data), A2L records the edge, building a
directed acyclic lineage graph that answers:

- "What data did this result come from?"
- "Which model and parameters produced this artifact?"
- "Has anyone derived something from this checkpoint before?"

A2L is designed to be lightweight and content-addressable: artifact identity is
based on a SHA-256 hash over the artifact type, URI, parameters, and parent IDs,
so identical computations produce the same artifact ID without duplication.

## Architecture

```
r4 CLI / SDK
      │
      ▼
Platform Gateway      /gw/a2l/*  ──▶  A2L Sidecar (port 8002)
                                            │
                                     PostgreSQL + pgvector
```

A2L runs as an independent FastAPI service that the gateway proxies.  It is
**not** part of UMRS and has **no hard dependency** on UMRS being deployed — it
can run standalone for pure provenance use-cases.

When A2L is not deployed, all `r4 artifact` and `r4 run` commands fail
fast with a clear error:

```
Error: A2L artifact service is not available on this deployment.
  hint: The `r4 artifact` commands require the A2L sidecar.
```

## Concepts

### Artifact

An artifact represents **any named, versioned computational output**.

| Field | Description |
|-------|-------------|
| `id` | Deterministic SHA-256 content address |
| `type` | Domain type string, e.g. `dataset`, `checkpoint`, `report`, `embedding` |
| `artifact_class` | Broad class: `dataset`, `model`, `pipeline_output`, `evaluation`, `other` |
| `uri` | Location of the artifact, e.g. `s3://bucket/path/file.pt` |
| `status` | Lifecycle: `pending` → `running` → `completed` / `failed` |
| `metadata` | Free-form JSON object (arbitrary domain annotations) |
| `project_id` | Owning project |
| `user_id` | Creator |
| `created_at` | ISO-8601 timestamp |

Artifact IDs are **content-addressable**: creating the same artifact twice with
the same type, URI, and parent set returns the existing ID rather than duplicating
the record.

### Lineage Edge

When artifact B is derived from artifact A, A2L records a directed edge `A → B`.
The graph can be traversed upward (ancestors / provenance) or downward
(descendants / impact analysis).

### Agent Execution

An **agent execution** is a record of one invocation of an automated agent or
pipeline step that consumed input artifacts and produced output artifacts.  It
captures:

| Field | Description |
|-------|-------------|
| `id` | UUID |
| `agent_name` | Logical name of the agent (e.g. `segmenter-v2`) |
| `agent_version` | Optional version string |
| `model_ref` | Model used (e.g. `Qwen/Qwen2.5-7B-Instruct`) |
| `prompt_hash` | SHA-256 of the prompt template for reproducibility |
| `params` | Execution parameters as JSON |
| `status` | `pending` → `running` → `completed` / `failed` / `cancelled` |
| `execution_trace` | Free-form JSON execution trace |
| `error` | Error message on failure |
| `started_at` / `completed_at` | Timestamps |

> **Note (2026-10-17):** the ledger records no artifact links on an agent
> execution — it has no input or output artifact fields, and earlier
> `--input` / `--output` values were silently dropped. `r4 run` no longer
> accepts them (`r4 agent-exec` refuses them with exit code 2). Record
> lineage between artifacts with `r4 artifact derive --parent <id>`.

## Workflow — Recording a Research Pipeline

The typical pattern for a pipeline step:

```bash
# 1. Register the raw input (admin / ingestion — no parent)
r4 artifact create \
  --type dataset \
  --uri s3://mylab/raw/experiment_2026.csv \
  --metadata '{"source": "fugaku", "experiment": "run-42"}' \
  --project mylab
# → returns: {"id": "sha256:<...>", "status": "pending", ...}

# 2. Start an agent execution (captures the agent intent before it runs)
r4 run create \
  --agent preprocessing-v3 \
  --version 3.1.0 \
  --model Qwen/Qwen2.5-7B-Instruct \
  --project mylab
# → returns: {"id": "<exec-uuid>", "status": "pending", ...}

# 3. Update the execution to "running"
r4 run update <exec-uuid> --status running

# 4. Derive the output artifact (links it to its parent)
r4 artifact derive \
  --type dataset \
  --uri s3://mylab/processed/experiment_2026_clean.csv \
  --parent sha256:<raw-dataset-id> \
  --metadata '{"step": "normalisation", "agent": "preprocessing-v3"}' \
  --project mylab
# → returns: {"id": "sha256:<derived-id>", ...}

# 5. Mark execution complete (the lineage edge is the derive in step 4)
r4 run update <exec-uuid> --status completed
```

## `r4 artifact` Commands

### List artifacts

```bash
r4 artifact list [--type TYPE] [--status STATUS] [--project ID]
                 [--user ID] [--limit N] [--offset N] [--json]
```

```bash
# All completed datasets in mylab
r4 artifact list --type dataset --status completed --project mylab

# JSON output, paginated
r4 artifact list --limit 20 --offset 40 --json
```

### Show a single artifact

```bash
r4 artifact show ARTIFACT_ID [--json]
```

```bash
r4 artifact show sha256:abc123...
```

### Create an artifact (ingestion / admin)

```bash
r4 artifact create --type TYPE --uri URI [--metadata JSON] [--project ID]
```

> **Note:** `create` registers an artifact without a provenance parent.
> Use this only for ingesting raw data or external inputs.
> For pipeline outputs, always use `derive`.

### Derive an artifact (preferred write path)

```bash
r4 artifact derive --type TYPE --uri URI \
                   --parent ID [--parent ID ...] \
                   [--metadata JSON] [--project ID]
```

Multiple `--parent` flags are accepted for merge/ensemble operations.

### Update artifact status

```bash
r4 artifact status ARTIFACT_ID {running|completed|failed} [--error MSG]
```

The server enforces an FSM — invalid transitions are rejected:
- `pending` → `running` ✓
- `running` → `completed` ✓
- `running` → `failed` ✓
- `completed` → anything ✗
- `failed` → anything ✗

### Inspect lineage

```bash
r4 artifact lineage ARTIFACT_ID [--direction {up|down|both}]
                                 [--depth N] [--json]
```

```bash
# Full provenance (both directions, depth 10)
r4 artifact lineage sha256:abc123...

# Ancestors only (what was this derived from?)
r4 artifact lineage sha256:abc123... --direction up

# Descendants (what has been derived from this?)
r4 artifact lineage sha256:abc123... --direction down --depth 5 --json
```

## `r4 run` Commands

### List executions

```bash
r4 run list [--agent NAME] [--status STATUS] [--project ID]
                   [--user ID] [--limit N] [--offset N] [--json]
```

### Show a single execution

```bash
r4 run show EXEC_ID [--json]
```

### Create an execution record

```bash
r4 run create --agent NAME [--version V] [--model REF] [--prompt-hash SHA256]
              [--params JSON] [--project ID]
```

`--params` is a free-form JSON object. The command prints the created record
as JSON.

### Update an execution

```bash
r4 run update EXEC_ID [--status {running|completed|failed|cancelled}]
                     [--error TEXT] [--trace JSON]
```

Status transitions:
- `pending` → `running` ✓
- `running` → `completed` / `failed` / `cancelled` ✓

## Matching and Idempotency

A2L uses **deterministic content-addressable IDs**.  If you attempt to `create`
or `derive` an artifact that already exists (same type, URI, parents, metadata),
the server returns the existing artifact rather than creating a duplicate.

This makes pipelines safe to re-run:

```bash
# Running this twice returns the same artifact ID both times
r4 artifact derive --type report --uri s3://mylab/report.md \
  --parent sha256:abc123 --project mylab
```

## Events (optional — requires Redis/KeyDB)

When A2L is deployed with a Redis sidecar, lifecycle events are published to a
Redis Stream (`a2l:events`).  External subscribers can consume these events to
trigger downstream pipelines.

```bash
# Check if events are available
curl -H "Authorization: Bearer $R4_API_KEY" \
  http://<gateway>/gw/a2l/events?limit=10

# Register a consumer group (for at-least-once delivery)
curl -X POST -H "Authorization: Bearer $R4_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"group": "my-pipeline", "consumer": "worker-1"}' \
  http://<gateway>/gw/a2l/events/subscribe
```

If Redis is not deployed, event endpoints return an empty list or `503` —
artifact CRUD and lineage operations continue to work normally.

## Checking A2L Availability

```bash
# Direct health check (from inside the deployment network)
curl http://a2l:8002/health
# → {"status": "ok", "service": "a2l"}

# Via gateway (from anywhere with a valid API key)
curl -H "Authorization: Bearer $R4_API_KEY" \
  http://<gateway>/gw/a2l/health

# Via r4 CLI — any a2l command fails fast if A2L is unreachable
r4 artifact list
```

## Deployment

A2L is included in the standard `docker-compose.e2e.yaml`.  For production
deployments, see [17. Docker/Compose Deployment](17-docker-deployment.md) and the
`gateway/sidecar/` and `a2l/` directories.

Required environment variables for the A2L container:

| Variable | Default | Description |
|----------|---------|-------------|
| `A2L_PORT` | `8002` | HTTP port |
| `DB_HOST` | `postgres` | PostgreSQL host |
| `DB_PORT` | `5432` | PostgreSQL port |
| `DB_NAME` | `e2e_test` | Database name |
| `DB_USER` | `postgres` | Database user |
| `DB_PASSWORD` | `postgres` | Database password |
| `REDIS_URL` | `""` | Redis URL (leave empty to disable events) |

The A2L database schema is created automatically on first startup via
`ensure_schema()`.

## Troubleshooting

| Symptom | Likely Cause | Fix |
|---------|-------------|-----|
| `Error: A2L artifact service is not available` | A2L container not running | Start A2L container; check gateway proxy config |
| `502 Bad Gateway` on `/gw/a2l/*` | A2L unhealthy | `docker logs a2l` to inspect startup errors |
| Artifact `create` returns existing artifact | Content-addressable dedup | Expected behaviour — same inputs = same ID |
| `status` update rejected with 422 | Invalid FSM transition | Check current status first with `r4 artifact show` |
| Events endpoint returns `503` | Redis not connected | Deploy Redis/KeyDB or ignore — not required for lineage |
| `hash_version` mismatch on old records | Schema migration needed | `r4 artifact show` still works; old IDs remain stable |
